======================================================================
1. DOCUMENT PURPOSE
======================================================================

This document defines a complete preliminary specification for an Election
Information Observatory consisting of three connected capabilities:

1. A live election tracker for following unofficial returns.
2. An immutable archival system that preserves what each monitored source
   published and when it was observed.
3. A comparison and analysis workbench for evaluating official returns,
   aggregator feeds, media reporting, race calls, corrections, and final
   certified results.

The system is intended to improve transparency and reproducibility. It must
not assume that a difference between two sources proves error, misconduct, or
intent. It must preserve provenance and make neutral comparisons possible.

Election-night results must always be represented as unofficial until the
responsible election authority completes the applicable canvass,
certification, recount, or amendment process.

======================================================================
2. PROJECT VISION
======================================================================

Working Name:
Election Information Observatory

Core Mission:
Continuously collect public election information from authoritative and
reporting sources, preserve each observed version, normalize the data without
destroying its original meaning, display current results in a live tracker,
and support time-aligned comparison from election night through certification.

Primary Questions the System Must Answer:

- What did an election authority report at a specific time?
- What did an aggregator or publisher display at that same time?
- Which races, counties, precincts, or ballot classes changed between updates?
- When did each source first display a result, statement, correction, or call?
- Was a numerical difference caused by latency, rounding, geographic scope,
  ballot inclusion, caching, correction, or another identifiable condition?
- How did election-night returns differ from canvassed and certified results?
- Can each displayed number be traced to the exact acquired source artifact?

Product Components:

A. LIVE TRACKER
   What is happening now?

B. DATA ARCHIVE
   What did every monitored source publish, and when was it observed?

C. INFORMATION TRACKER
   What were aggregators and reporting organizations showing or saying?

D. ANALYSIS WORKBENCH
   How do source streams compare with one another and with certified results?

3. GUIDING PRINCIPLES
======================================================================

3.1 Provenance First
Every normalized observation must link back to an original acquired artifact,
source URL, acquisition timestamp, collector version, parser version, and
cryptographic hash.

3.2 Append-Only History
New observations must be appended. Existing historical observations must not
be silently overwritten because later totals differ.

3.3 Separate Observation Types
The system must distinguish:

- OBSERVED: A source displayed or supplied a value.
- DERIVED: The application calculated a value from observations.
- ESTIMATED: A model or source estimated an unknown quantity.
- REPORTED: A publisher or person made a statement.
- CALLED: A source projected or called a race.
- UNOFFICIAL: A preliminary result published before certification.
- CERTIFIED: A result formally certified by the applicable authority.

3.4 Neutral Comparison
The system may identify discrepancies, latency, revisions, or conflicts. It
must not infer intent merely from a difference.

3.5 Source Language Preservation
The original terminology must be retained alongside normalized values. For
example:

source_label: "Partially Reporting"
normalized_status: "PARTIAL"

3.6 Evidence Preservation Before Parsing
The original response must be stored before a parser transforms it.

3.7 Graceful Degradation
If a parser fails, the raw acquisition should still be archived and visible as
an unparsed artifact.

3.8 Operational Respect
Collectors must respect documented APIs, rate limits, terms of service,
robots directives, licensing restrictions, and the operational sensitivity of
public election infrastructure.

7.3 Polling Policy

Recommended starting intervals:

- Before polls close: every 5 minutes
- Poll close through peak reporting: every 15 to 30 seconds
- Active but slowing: every 60 seconds
- No material change for 30 minutes: every 2 to 5 minutes
- Following morning: every 15 minutes
- Canvass period: every 1 to 6 hours
- Certification period: daily

Each policy must support:

- Per-source override
- ETag and If-Modified-Since requests
- Exponential backoff
- Random jitter
- Host-level concurrency limit
- Retry budget
- Circuit breaker
- Emergency stop
- Manual pause
- Election-night priority level

7.4 Immutability

- Raw artifacts must be write-once from the application perspective.
- Object versions must not be deleted by normal application credentials.
- Retention controls should be enabled.
- A second administrative boundary should receive replicated copies.
- Metadata corrections must be appended rather than replacing evidence.

7.5 Cryptographic Integrity

Required:

- SHA-256 for every artifact
- Signed hourly manifest
- Daily manifest
- Artifact count and total byte count in each manifest
- Optional Merkle tree root for each hourly batch
- Signing-key identifier
- Signature verification utility
- System-clock health record

Recommended advanced control:

- RFC 3161 trusted timestamps for periodic manifests

9. EVENT-SOURCED PROCESSING ARCHITECTURE
======================================================================

Processing Flow:

1. Scheduler creates collection job.
2. Collector requests source.
3. Raw response and headers are archived.
4. Hash is calculated.
5. Acquisition metadata is recorded.
6. Parser reads archived artifact.
7. Parser emits source-faithful observations.
8. Normalizer maps observations to canonical entities.
9. Validator checks internal consistency.
10. Event store appends normalized events.
11. Materializer creates current-state views.
12. Tracker API serves current and historical states.
13. Comparison engine aligns source observations by time.
14. Manifest service signs archival batches.

No processing stage may destroy or replace the raw artifact.

10. COMPARISON AND ANALYSIS ENGINE
======================================================================

10.1 Comparison Operations

- Official totals versus aggregator totals
- Official totals versus publisher-displayed totals
- Source update time versus first observed time
- First lead change by source
- First race call by source
- Source correction timeline
- Election-night total versus certified total
- Candidate percentage drift over time
- Reporting-unit inclusion over time
- Ballot-method inclusion over time
- Source latency distribution
- Missing update detection
- Duplicate update detection
- Retroactive content change detection

10.2 Comparison Rules

A difference must not be labeled an error until the system has evaluated:

- Timestamp alignment
- Geographic scope
- Contest identity
- Candidate identity
- Vote-method scope
- Rounding
- Cache age
- Corrected official source data
- Partial versus full reporting
- Source-generated versus estimated reporting percentages

10.3 Time Alignment

Supported alignment methods:

- Nearest observation before event
- Nearest observation after event
- Nearest observation within tolerance
- Exact source timestamp
- First system-observed timestamp

Default media comparison:
Use the latest official observation obtained at or before the reporting event,
while also showing the first later official observation.

10.4 Discrepancy Severity

Suggested neutral classifications:

- MATCH: Values agree after allowed rounding.
- LATENCY_EXPLAINED: Publisher matches an older official snapshot.
- SCOPE_MISMATCH: Sources cover different jurisdictions or ballot subsets.
- ROUNDING_ONLY: Difference is explained by displayed precision.
- SOURCE_REVISION: Source changed a prior value.
- UNRESOLVED_DIFFERENCE: Difference remains after automated checks.
- DATA_UNAVAILABLE: Required evidence is missing.

These labels describe evidence state, not intent.

16. LEGAL, LICENSING, AND ETHICAL CONTROLS
======================================================================

Before collection from a source, review:

- Terms of service
- API license
- Copyright restrictions
- Database rights where applicable
- Robots instructions
- Rate-limit requirements
- Republishing restrictions
- Quotation limits
- Screenshot retention policy
- Personal data handling

Media Content Policy:

- Prefer structured facts and short excerpts.
- Store links and metadata.
- Do not republish complete copyrighted articles without permission.
- Preserve complete content only where legally authorized or operationally
  justified, with access restrictions if necessary.

Neutrality Policy:

- Apply identical collection and comparison rules across parties and
  candidates.
- Publish methodology.
- Distinguish observation from interpretation.
- Disclose source gaps.
- Do not present unresolved discrepancies as proof of wrongdoing.

2. The system archives the corresponding official web presentation.
3. Every artifact receives a SHA-256 hash and acquisition timestamp.
4. Parsed observations link back to raw artifacts.
5. The tracker displays current unofficial contest results.
6. Users can drill down to county results where available.
7. Users can select an earlier time and reconstruct the known state.
8. Users can see changes between two observations.
9. Users can compare at least four independent source presentations.
10. Race calls are stored separately from official results.
11. Corrections and retractions create new events.
12. Source failures and parser failures generate alerts.
13. The archive produces signed manifests.
14. The system reconciles election-night results against certified results.
15. The public interface clearly labels unofficial data.
16. The system passes a historical replay test.
17. A full election-night rehearsal succeeds before production use.

21. KEY RISKS AND MITIGATIONS
======================================================================

RISK: Source structure changes on election night.
MITIGATION: Platform adapters, schema monitoring, raw capture, HTML fallback,
and pre-election rehearsals.

RISK: Aggressive polling burdens election infrastructure.
MITIGATION: Conditional requests, rate limits, backoff, source-specific
policies, and emergency disable controls.

RISK: Source timestamps are ambiguous.
MITIGATION: Preserve displayed time, request time, response time, parse time,
and first-observed time separately.

RISK: Precinct reporting percentage is treated as ballot completion.
MITIGATION: Store source measure exactly and do not relabel it as percentage
of votes counted.

RISK: Candidate or contest mappings are wrong.
MITIGATION: Canonical IDs, source crosswalks, manual review, and validation
against ballot definitions.

RISK: A discrepancy is mischaracterized.
MITIGATION: Automated scope, latency, rounding, ballot-type, and revision
checks before classifying an unresolved difference.

RISK: Public dashboard compromise affects evidence.
MITIGATION: Isolate public services from collectors and immutable archives.

RISK: Copyright or license violation.
MITIGATION: Source-by-source legal review, short excerpts, metadata-first
retention, and licensed APIs where required.

RISK: Missing historical context.
MITIGATION: Continue collection through canvass, recount, certification, and
amendment.

24. FINAL PROJECT DEFINITION
======================================================================

The Election Information Observatory is an append-only,
provenance-preserving election information platform. It collects official
results, aggregator feeds, reporting presentations, calls, corrections, and
final certifications. It exposes live unofficial returns through an election
tracker while preserving each monitored source observation for later
reconstruction and neutral comparison.

Its defining capability is not merely showing who is ahead. Its defining
capability is showing what was known, what was reported, by whom, from which
artifact, and at what time, while preserving a reproducible path from every
screen value back to the original evidence.
